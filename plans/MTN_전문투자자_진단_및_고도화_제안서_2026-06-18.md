# MTN 전문투자자 관점 진단 및 고도화 제안서

> 제안 대상: MTN 운영·제품·투자전략 책임자
> 기준일: 2026-06-18
> 진단 범위: 현재 워크스페이스 코드, 자동화 테스트, 운영 배포 접근성, 데이터 계보, 점수 산식, 투자 전 과정 UX

## 1. 제안 요약

MTN은 `시장 판단 → 후보 발굴 → 다단계 검증 → 매매 계획 → 포트폴리오 관리 → 복기`를 한 제품 안에 연결한 점이 강점입니다. 개인용 스크리너를 넘어 투자 의사결정 지원 시스템으로 발전할 기반은 이미 갖췄습니다.

다만 현재 상태를 전문투자자가 실자금 의사결정에 사용하는 수준으로 평가하면 **조건부 사용 가능**입니다. 가격·패턴 기반 후보 탐색과 매매 규율 보조에는 유용하지만, 다음 세 가지 이유로 점수와 상태값을 그대로 투자 판단의 근거로 사용하기에는 위험합니다.

1. 매크로 점수에 경제적 의미를 바꾸는 P0 산식 오류가 있습니다.
2. 일부 화면의 `업데이트 시각`은 원천 데이터 시각이 아니라 API 응답 생성 시각입니다.
3. 전략 점수에 대한 아웃오브샘플 검증, 비용 반영 백테스트, 성과·위험 귀속 체계가 없습니다.

따라서 고객사에는 MTN을 현재 **주문·운용 시스템이 아니라 리서치 및 규율 보조 도구**로 정의하고, 90일 동안 `데이터 신뢰성 → 모델 검증 → 포트폴리오 운용 기능` 순으로 고도화할 것을 제안합니다.

## 2. 진단 방법과 한계

- 전체 페이지, API, 데이터 제공자, 핵심 산식과 테스트를 코드 수준에서 검토했습니다.
- `npm test`를 직접 실행했으며 현재 테스트 스위트는 전부 통과했습니다.
- 운영 주소는 로그인 화면으로 정상 리다이렉트되었고 비인증 API는 `401 Authentication required`를 반환했습니다.
- 로컬 개발 서버는 기존 프로세스 잠금이 있으나 해당 포트가 응답하지 않아 실제 화면의 로그인 후 데이터까지 재현하지 못했습니다.
- 따라서 본 문서에서 **확정**은 코드·테스트로 재현된 사항, **운영 확인 필요**는 인증 후 화면에서 최종 확인해야 하는 사항입니다.

## 4. 현재 업데이트가 제대로 되지 않는 부분

### 4.1 P0: 업데이트 시각이 원천 데이터 시각을 의미하지 않음

`/api/macro`와 `/api/master-filter`는 응답을 만들 때 `new Date().toISOString()`을 `asOf/updatedAt`에 기록합니다. 원천 가격의 마지막 거래일, FRED 관측일, KIS 체결 시각과 독립적입니다. 휴장일·제공자 장애·캐시 적중 상황에서도 화면은 최신처럼 보일 수 있습니다.

**고객사 영향:** 투자자는 신선도 배지를 신뢰해 오래된 상태값으로 신규 진입을 결정할 수 있습니다.

**제안:** 각 지표에 `observedAt`, `fetchedAt`, `calculatedAt`, `source`, `marketSession`, `expectedDelay`, `isStale`, `fallbackReason`을 분리 저장하고, 복합 점수는 가장 오래된 필수 입력의 시각을 대표 시각으로 사용합니다.

근거: `app/api/macro/route.ts`, `app/api/master-filter/route.ts`

### 4.2 P0: 운영 최신성 검증을 제품 내부에서 확인하기 어려움

운영 API는 인증으로 보호되어 있는 점은 적절하지만, 사용자 화면에서 데이터 제공자별 최종 성공·실패·지연 상태를 한곳에서 확인하는 운영 콘솔은 제한적입니다. 관리자 캐시 화면은 존재하지만 투자 화면의 상태값과 한 번에 대사하는 기능은 없습니다.

**제안:** “Data Health” 패널을 추가해 KIS, Yahoo, FRED, DART/SEC, Supabase 배치의 마지막 성공 시각과 사용 중인 폴백을 표시합니다. 신선도 SLA를 초과하면 점수 대신 `판정 보류`를 반환합니다.

### 4.3 P1: 포트폴리오 자동 갱신은 개선됐으나 운영 반영 확인 필요

현재 작업 트리의 포트폴리오 화면에는 3분 자동 갱신이 추가되어 과거의 1회성 조회 문제는 개선됐습니다. 다만 변경 사항이 아직 작업 트리에 있고 운영 배포본은 로그인 후 확인하지 못했습니다. 오류 발생 시 자동 갱신도 중단되는 구조입니다.

**제안:** 장중/장외 주기를 분리하고, 오류 시 지수 백오프로 재시도하며, 마지막 성공 가격 시각을 포지션별로 표시합니다.

근거: `app/portfolio/page.tsx`

## 5. 맥락이 맞지 않는 부분

### 5.1 P0: `^IRX`를 2년물로 해석

매크로 엔진은 `^TNX - ^IRX`를 “10Y-2Y 스프레드”로 설명합니다. 그러나 Yahoo Finance의 `^IRX`는 **13주 미국 국채**입니다. 현재 계산은 10년-3개월에 가깝고 10년-2년이 아닙니다. 두 곡선은 경기침체 신호의 의미와 반응 시점이 다릅니다.

**제안:** 이미 구현된 FRED `DGS10`, `DGS2`를 실제 계산에 사용하고, 데이터가 없으면 점수를 중립 처리하거나 명시적으로 10Y-3M 모델로 이름을 바꿉니다. [Yahoo Finance의 ^IRX 정의](https://finance.yahoo.com/quote/%5EIRX/)

근거: `app/api/macro/route.ts`, `lib/macro/compute.ts`, `lib/data/fred.ts`

### 5.2 P0: HY OAS의 `%` 단위를 `bp`로 처리

FRED `BAMLH0A0HYM2` 원자료 단위는 Percent인데 코드는 값을 그대로 basis point 임계값 300/400/500과 비교합니다. 예를 들어 3.5%는 350bp로 변환해야 하지만 현재 계산에서는 3.5로 비교됩니다. 이 경우 크레딧 항목이 구조적으로 과대평가될 가능성이 큽니다. 추세 보정 임계값 `±30`도 같은 단위 문제를 가집니다. [FRED 시리즈 단위](https://fred.stlouisfed.org/series/BAMLH0A0HYM2)

**제안:** 수집 직후 `% × 100 = bp`로 정규화하고 타입명도 `oasPct`와 `oasBps`로 분리합니다. 2007-2009, 2020, 2022 구간을 회귀 테스트에 포함합니다.

근거: `lib/data/fred.ts`, `lib/macro/compute.ts`

### 5.3 P0: 한국 화면에도 미국 중심 매크로 regime 결합

Command Center와 Market Context는 시장을 KR로 전환해도 `/api/macro`를 시장 파라미터 없이 호출합니다. 이 API의 주요 가중치는 미국 HY OAS, VIX, UUP, TLT, 미국 수익률곡선, IWM/SPY입니다. 한국 마스터필터와 미국 매크로 regime이 한 화면에서 동일한 의사결정 문맥으로 합쳐집니다.

**제안:** `macro?market=US|KR`로 분리합니다. 한국은 원/달러, KOSPI/KOSDAQ 시장 폭, 외국인·기관 수급, 한국 금리곡선, 반도체/수출 민감도 등을 핵심 모델로 두고 미국 regime은 글로벌 overlay로 별도 표시합니다.

근거: `hooks/useCommandCenterSummary.ts`, `contexts/MarketContext.tsx`, `app/api/macro/route.ts`

### 5.4 P1: 시장 폭과 NH/NL이 종목 유니버스가 아니라 ETF 표본

마스터필터의 `Above 200D`와 `NH/NL`은 실제 상장 종목 전체가 아니라 소수의 주요 ETF가 200일선 위인지, 52주 고저점 근처인지로 계산됩니다. UI에는 proxy라고 표시되지만 20점씩 부여되어 전체 100점에 큰 영향을 줍니다.

**고객사 영향:** 몇 개 ETF의 움직임이 광범위한 종목 참여도로 오인될 수 있습니다.

**제안:** 거래소별 유동성 필터를 통과한 종목 유니버스에서 `% above 20/50/200DMA`, 실제 NH-NL, A/D line, up/down volume을 계산합니다. ETF 값은 장애 시 폴백으로만 사용하고 점수 신뢰도를 낮춥니다.

근거: `app/api/master-filter/route.ts`, `lib/master-filter/compute.ts`

### 5.5 P1: 포트폴리오 노출과 현금이 취득원가 중심

포트폴리오의 `investedCapital`, 섹터 노출, 개별 노출은 주로 `보유수량 × 평균 진입가`로 계산됩니다. 총자산이 현재 평가액이어도 노출은 취득원가이므로 큰 수익·손실 이후 섹터 집중도와 현금 비중이 실제 시가 기준과 달라질 수 있습니다.

**제안:** `marketValue = shares × currentPrice`를 노출의 기본값으로 하고, 취득원가는 P&L 용도로 분리합니다. 가격이 오래됐거나 없으면 해당 포지션을 `risk unknown`으로 처리합니다.

근거: `lib/finance/core/portfolio-risk.ts`

## 6. 전문투자자 기능과의 괴리

### 6.1 잘 구현된 영역

- 전략별 후보 탐색: SEPA, CAN SLIM, VCP, Qullamaggie, 리더·모멘텀을 독립 엔진으로 분리했습니다.
- 규율 강제: 손절 유효성, 단일 거래 위험, portfolio heat, sector risk, market HALT를 게이트로 연결했습니다.
- 데이터 출처 표시: RS의 DB/Universe/Benchmark Proxy 구분과 일부 데이터 품질 플래그가 있습니다.
- 투자 라이프사이클: 계획, 체결, 피라미딩, 부분매도, 스냅샷, 3-layer 복기가 연결됩니다.
- 회귀 안정성: 핵심 계산과 라이프사이클 테스트가 폭넓게 존재하고 현재 모두 통과합니다.

### 6.2 괴리가 큰 영역

| 영역 | 현재 MTN | 전문 운용에서 기대하는 수준 | 의견 |
|---|---|---|---|
| 전략 검증 | 예제·경계값 단위 테스트 중심 | 생존편향 없는 유니버스, 워크포워드, 비용·슬리피지, 용량 분석 | 가장 큰 구조적 공백 |
| 포트폴리오 위험 | 포지션·섹터·손절 리스크 | 시가·FX·상관·팩터·유동성·스트레스·VaR/ES | 포지션 단위 규율에는 유용, 포트폴리오 위험에는 부족 |
| 성과 분석 | P&L, R-multiple, 실수 태그 | TWR/MWR, benchmark excess return, attribution, hit rate by regime | 투자 프로세스의 엣지를 입증하기 어려움 |
| 데이터 거버넌스 | 제공자·폴백 일부 표시 | point-in-time 데이터, 수정 이력, corporate action, SLA, reconciliation | 숫자의 재현성과 감사 가능성 부족 |
| 주문·실행 | 계획·체결 기록 | 주문상태, 부분체결, 수수료·세금·슬리피지, liquidity/impact | README 정의대로 OMS가 아니므로 기능 경계 명시 필요 |
| 모델 거버넌스 | 하드코딩 가중치와 설명 | 모델 버전, 승인자, 변경 사유, 챔피언/챌린저, drift | 전문 조직 도입 전 필수 |
| 컴플라이언스 | 인증·RLS·감사 일부 | 역할 분리, 승인 워크플로우, 불변 감사로그, 리포트 보존 | 고객사 조직 규모에 맞춰 단계 도입 |

FINRA는 알고리즘 전략에 대해 독립적 테스트, 데이터 무결성 검증, 변경 승인, 버전 보존, 실시간 모니터링을 권고합니다. MTN이 주문을 직접 내지 않더라도 점수가 투자 결정을 유도한다면 같은 수준의 모델 통제가 유용합니다. [FINRA Regulatory Notice 15-09](https://www.finra.org/industry/notices/15-09)

### 6.3 현재 전략별 의견

**SEPA/VCP:** 추세 템플릿과 수축 구조를 설명 가능한 규칙으로 만든 점은 좋습니다. 다만 펀더멘털은 참고 정보이며 누락 시 저장을 막지 않습니다. 이는 “기술적 셋업 스크리너”로는 타당하지만 “Minervini 전체 프로세스 통과”로 표현하면 과장입니다.

**CAN SLIM:** 데이터 커버리지와 confidence를 노출하는 방향은 적절합니다. 다만 기관 수급 등 일부 데이터가 부족해도 전체 실패를 피하도록 완화되어 있습니다. 따라서 `PASS`보다 `가격·가용 펀더멘털 기준 PASS`처럼 범위를 명시해야 합니다.

**Leader/Qullamaggie/Surge:** 구현은 설명 가능한 휴리스틱이나 가중치와 등급 경계의 실증 보정 근거가 저장소에서 확인되지 않습니다. “전문가 전략을 구현했다”기보다 “전략 철학을 정량 근사한 후보 랭커”로 정의하는 것이 정확합니다.

**Macro/Master Filter:** 포지션 크기 조절에 활용하려는 방향은 좋지만, 앞서 지적한 단위·심볼·시장 맥락 오류가 해결되기 전까지는 자동 HALT/REDUCED의 단독 근거로 사용하지 않아야 합니다.

## 7. 신규 기능 제안

### 7.1 Model Validation Lab

모든 전략을 동일한 조건으로 비교하는 연구 환경입니다. 시점별 유니버스, 상장폐지 종목, 기업행사, 거래비용을 포함하고 walk-forward 결과를 저장합니다.

**고객 가치:** “그럴듯한 점수”를 “재현 가능한 투자 근거”로 바꿉니다. 전략별 CAGR보다 hit rate, expectancy, MDD, turnover, capacity, regime별 성과를 함께 보여야 합니다.

### 7.2 Portfolio Risk Cockpit

시가·FX 환산 노출, 상관 클러스터, 섹터·국가·통화·스타일 팩터, 유동성 일수, 예상손실, 스트레스 시나리오를 제공합니다.

**고객 가치:** 개별 종목 손절을 잘 관리해도 같은 팩터에 몰리면 포트폴리오는 한 번에 무너질 수 있습니다. 종목 수가 아니라 공통 위험원을 관리해야 합니다.

### 7.3 성과·의사결정 귀속

수익을 종목선정, 시장타이밍, 포지션 사이징, 피라미딩, 청산, 섹터 배분, 환율로 나눕니다. CFA Institute도 성과 측정, 귀속, 평가를 연결하고 총 포트폴리오 수익·위험과 조정할 것을 강조합니다. [CFA Institute Portfolio Performance Evaluation](https://www.cfainstitute.org/insights/professional-learning/refresher-readings/2025/portfolio-performance-evaluation)

**고객 가치:** 잘된 거래와 잘된 프로세스를 구분해 다음 자본 배분에 반영할 수 있습니다.

### 7.4 신호 변화 설명과 What-if

“어제 GREEN에서 오늘 YELLOW가 된 이유”, “VIX가 5포인트 오르면 허용 위험이 어떻게 바뀌는지”, “이 종목을 추가하면 섹터·팩터 위험이 얼마나 증가하는지”를 사전 계산합니다.

**고객 가치:** 결과값 확인 시간을 줄이고 투자위원회 설명 가능성을 높입니다.

### 7.5 이벤트·캘린더 위험

실적 발표, 배당락, 유상증자, 보호예수, FOMC, CPI, 옵션만기와 포지션의 날짜를 연결합니다. 이벤트 전후의 허용 위험과 신규 진입 정책을 자동 조정합니다.

**고객 가치:** 기술적 패턴이 좋아도 단일 이벤트로 손절 범위를 뛰어넘는 갭 위험을 관리할 수 있습니다.

### 7.6 투자위원회용 근거 패키지

후보별 원천 데이터 시각, 점수 버전, 통과·탈락 근거, 반대 논리, 시나리오, 최종 승인자를 한 PDF/화면으로 묶습니다. LLM 의견은 근거와 데이터 시점을 함께 저장하고 정량 점수를 덮어쓰지 않도록 분리합니다.

**고객 가치:** 투자 판단의 재현성, 내부 검토 속도, 사후 감사 품질이 향상됩니다.

## 10. 최종 제안

MTN의 다음 경쟁력은 스캐너 수를 늘리는 데 있지 않습니다. 이미 충분한 전략 엔진이 있습니다. 우선순위는 **숫자의 신뢰성, 모델의 검증 가능성, 포트폴리오 차원의 설명력**입니다.

고객사에는 다음과 같이 제안합니다.

> MTN을 현재의 “다전략 후보 탐색 및 매매 규율 플랫폼”에서, 데이터 시점과 모델 근거를 감사할 수 있고 포트폴리오 전체 위험과 성과 원인을 설명하는 “전문 투자 의사결정 운영체계”로 고도화합니다. 1단계에서 산식과 신선도를 바로잡고, 2단계에서 실증 검증을 통과한 모델만 승격하며, 3단계에서 포트폴리오 위험·성과 귀속과 투자위원회 워크플로우를 연결합니다.

현재 구현은 폐기 대상이 아니라 좋은 기반입니다. 다만 P0 항목을 수정하기 전에는 매크로 점수와 자동 진입 허용 상태를 참고 신호로만 사용하고, 최종 투자는 원천 데이터와 별도 리스크 검토를 거쳐야 합니다.
