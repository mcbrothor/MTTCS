# MTN 추천·텔레그램 복구 및 시스템 최적화 계획

작성 기준: 2026-09-21 00:47 KST부터 실시한 점검. 운영 웹, 로컬 프로세스, 로그, 운영 DB의 읽기 전용 조회 및 현재 코드 검증을 바탕으로 작성했다. 이번 작업에서는 재배포, DB 마이그레이션, 워커 재시작, 큐 등록, 텔레그램 발송을 실행하지 않았다.

## 1. 결론과 기존 보고 정정

웹 배포는 완료됐지만 추천 시스템 전체의 운영 반영과 완료 검증이 빠졌다. 우선순위는 **로컬 워커 갱신 → 누락된 DB 마이그레이션 적용 → 시장별 생성·전송 경로 복구 → 실제 예정 보고 검증**이다.

- Vercel `/api/release`는 `94a46adce5d802a89fd31378376a685d6a0421bc`를 반환한다. 웹 배포 성공 자체는 확인된다.
- 추천 워커 PID 1756은 9월 7일에 시작한 프로세스다. 9월 14일 수정 이전의 오류 문구가 9월 20일까지 반복된다. 수정된 코드가 장기 실행 프로세스에 반영되지 않은 강한 증거다. 워커가 자신의 실행 SHA를 보고하지 않아 메모리에 로드된 정확한 커밋을 직접 조회할 수는 없다.
- 9월 11~20일 일일 추천 실행 10건은 모두 같은 나스닥 목록 오류로 실패했다. 해당 기간에 저장된 후보는 0건이며 현재 pending/processing 실행은 없다. 이전 답변의 ‘backlog 처리 중’ 설명은 확인된 상태와 다르다.
- 9월 18일 KOSPI200 종가베팅의 SENT는 추천 성공을 뜻하지 않는다. 저장 결과는 `BLOCKED`, 풀 29/200, 추천 0건이다. KOSDAQ150은 당일 최종 스냅샷이 없다.
- 현재 Node 24에서 전체 195개 테스트 파일이 통과했고, 수정된 나스닥 파서는 현재 공개 응답에서 고유 종목 101개를 읽었다. 이전 Node 20 테스트 실패와 운영 워커의 구버전 실행은 별개 문제다. 단위 테스트 통과가 실제 추천 발행 성공을 뜻하지는 않는다.

## 3. 실행 계획

### Wave 1 — 운영 반영 복구 (최우선, 예상 반나절)

1. 실행 중인 작업·잠금·최근 전송 영수증을 확인하고 배포할 커밋을 고정한다. 테스트와 운영 관리 명령은 지원되는 동일 Node 버전으로 실행한다.
2. 웹과 별도로 로컬 추천 워커를 최신 코드로 교체한다. 기존 작업을 정상 종료한 뒤 교체하며, 재시작 후 새 PID·시작시각·수집 결과를 확인한다. 단순 kickstart는 이미 실행 중인 워커를 교체하지 않는다.
3. DB 함수 정의와 마이그레이션 이력을 보관한 후 누락된 `20260914010000`을 적용한다. `pg_get_functiondef`로 일반 280초·종가 240초 및 대응 수집기 판정을 확인한다. 이력에 기록됐다는 사실만으로 적용 성공을 판단하지 않는다.
4. 웹, 로컬 워커, DB, 외부 감시기의 적용 버전을 각각 기록한다. 9/14 변경의 Cloudflare/GitHub 감시기 반영 여부도 확인한다.

완료 기준: 새 워커에서 수정된 목록 수집 성공, DB 실제 정의 일치, 중복 워커 없음, 기존 발송 영수증 보존. 웹 401 응답 검증은 접근 통제 확인으로 유지하되 업무 완료 판정과 분리한다.

### Wave 2 — 생성·전송 경로 복구 (예상 1~2일)

1. **시장별 실패 격리:** NASDAQ100·SP500·KOSPI200·KOSDAQ150 각각 목록 수집·분석·발행 상태를 저장한다. 초기 목록 조회부터 오류를 분리하고, 프롬프트·파싱·‘4개 시장 모두 10개’ 검증까지 시장별 작업 계약으로 바꾼다. 나스닥 오류를 catch하는 것만으로는 후속 전체시장 검증에서 다시 실패할 수 있다.
2. **종가 원본 풀 복구:** KOSPI 29개로 축소된 공급원·종목 필터·캐시 경로를 재현한다. KOSDAQ 실패도 원인 단계와 오류 코드를 구분한다. 원본 목록 수와 시세 수집 수를 별도로 기록하고 기존 95% 수집 기준을 유지한다. 완전한 입력이 확보되면 예정 시간에 FINAL을 생성한다.
3. **미전송 보관함 통합:** 공식 추천·관찰 보고·보류 안내를 명시적 메시지 종류로 관리한다. 관찰 보고를 공식 추천으로 승격하지 않고, 해당 보고가 원래 전송 대상인지 동일한 판정 함수로 생성·재시도·완료 동기화에 적용한다.
4. **전송 잠금·영수증 보강:** 보고·수신처·청크별 식별자와 CLAIMED/SENT/FAILED/UNCERTAIN 상태를 공유 저장소에서 관리한다. CLAIMED는 임대 만료와 소유권을 확인하며, 응답 유실 등 UNCERTAIN은 성공 여부 확인 없이 재전송하지 않는다. Telegram과 DB 사이의 엄밀한 exactly-once를 보장한다고 표현하지 않는다.
5. **업무 기준 상태 판정:** 장중 FINAL의 존재, 수집률, 추천/보류 상태, 메시지 ID를 검사한다. 시간대 밖 skipped는 중립 상태이며 앞선 발행 실패를 정상으로 덮지 않는다. 시장 휴장일·발행 예정시각도 판정에 반영한다.

완료 기준: 한 시장 공급원을 강제로 실패시켜도 나머지 시장의 보고가 완료됨; SHADOW 전송 실패 후 안전한 재시도 성공; 일부 청크 실패·응답 유실·워커 재시작 시 중복/누락 처리 검증; 종가 최종 누락이 올바르게 경고됨.

### Wave 3 — 누락 보고 복구 및 실제 운영 검증

1. 날짜·시장별로 생성 실패, 미전송, 이미 전송, 결과 불확실, 유효기간 만료를 조회한다. 전송 미확인 전체를 일괄 SENT 초기화하거나 강제 재발송하지 않는다.
2. 저장된 유효 보고는 실패한 수신처·청크만 전송하고 Telegram message_id와 DB 완료 상태를 대조한다.
3. 과거 날짜의 후보가 없는 생성 실패는 현재 시세로 재실행해 과거 추천처럼 표시하지 않는다. 기준시점 데이터를 확보할 수 있을 때만 과거 검토 보고로 재현하며, 그렇지 않으면 생성 실패와 데이터 부재를 안내한다.
4. 유효시간이 지난 종가베팅은 당일 실전 추천으로 재발송하지 않는다. 원래 저장본이 있으면 날짜와 만료 사실을 표시한 복기 자료로 전달한다. 현재 유효 추천은 최신 거래 세션과 현재 데이터 기준으로 새로 산출한다.
5. 실제 예정 보고를 연속 2거래일 관찰한다. 네 시장의 예정 보고와 국내 두 시장의 종가 결과가 누락 없이 저장·전송되는지 확인한다. 적격 종목이 0개이면 명확한 보류 보고도 정상 결과지만 데이터 장애와 구분한다.

완료 기준: 시장별 예정 보고의 저장 결과와 Telegram 영수증 일치, 반복 장애 알림·중복 발송 0건, 원인 미상 장기 pending/processing 0건. 추가 장기 안정성 확인은 5거래일 추적을 권장한다.

| P2 | 메모리·전력 정책을 사용자 입력뿐 아니라 서버 작업량과 발행 마감시간에도 연동 | 24~48시간 메모리 압박·swap 증가율·작업시간·전력을 함께 측정. 고비용 LLM 1개 상주를 초기 기준으로 평가하고 마감 작업 중 저전력 전환 영향을 확인. |

9/21 단일 관측에서 메모리 24GB 중 약 23GB 사용, swap 약 39GB 사용이 관찰됐다. 이는 자원 압박의 조사 근거이며, 나스닥 파싱 오류나 개별 타임아웃의 직접 원인으로 확정할 수 없다. swap 총량에는 과거 부하가 반영될 수 있다. 사용자 작업 중인 VM의 상태 변경은 별도로 다룬다.

자원 관리 정책도 실행본과 저장소가 다르다. 저장소의 최신 정책은 전력 모드 제어를 포함하지만 실제 실행은 사용자 경로의 이전 복사본이며, root daemon과 해당 상태파일은 확인되지 않았다. 사용자 경로 상태파일은 갱신되고 있어 관리 작업 전체가 중단됐다고 볼 수는 없다. 현재 정책의 동작 범위를 확인한 뒤 필요한 설치본만 갱신한다.

워커 수를 늘리기 전 heartbeat 충돌키도 점검한다. 현재 component 단위 upsert는 여러 워커의 상태를 덮을 수 있으므로 worker_id를 포함한 관측과 공통 작업 잠금이 먼저 필요하다.

AI 모델 변경이나 메모리 증설부터 시작하지 않는다. 우선 실행 버전 불일치·시장 간 실패 전파·중복 수집을 해결한 후 자원 측정 결과에 따라 결정한다.

## 5. 운영 도구와 검증 보완

이전 조회 과정의 `node -e ... -- --dry-run` 호출은 스크립트의 `process.argv.slice(2)`와 맞지 않아 dry-run 옵션이 누락됐다. 실제로 장애 알림과 9/19 큐 등록이 발생했다. 해당 큐도 이후 같은 파싱 오류로 실패했다. 이를 성공적인 추천 복구로 집계해서는 안 된다.

후속 구현에서는 진단 명령과 실행 명령을 분리하고, 관리 명령은 기본 dry-run으로 만들며 명시적인 apply 인자를 검증한다. 직접 파일 실행·import·`node -e` 경로의 인자 테스트를 추가한다. 조회는 상태 변경 가능한 워커/감시기 진입점 대신 SELECT 전용 함수를 사용한다.

회귀 검증에 추가할 시나리오:

1. 나스닥 목록 변경·부분 목록·공급원 503·저장본 만료.
2. 한 시장 실패 시 다른 시장 독립 완료 및 빈 후보의 보류 처리.
3. 장중 FINAL 실패 후 시간대 밖 skipped 응답이 발생하는 순서.
4. 관찰 보고의 재전송과 수신처·청크별 부분 실패, 불확실 응답.
5. 작업 중 워커 교체, 구버전 heartbeat, 임대 잠금 만료.
6. DB 타임아웃 마이그레이션 적용 전후 실제 함수와 스케줄 실행 결과.
7. 과거 날짜 재처리 시 현재 시세가 과거 추천으로 저장되지 않는지 확인.

배포 실패 시에는 영향받은 기능의 신규 실행을 일시 보류하고, 기록한 이전 웹/워커 버전과 호환성을 확인해 복귀한다. DB는 변경 전 정의와 의존성을 검토한 전진 수정 또는 검증된 복구 절차를 사용하며, 추천 데이터·전송 영수증은 보존한다.

## 6. 예상 일정과 최종 완료 판정

복구 및 코드 보강은 약 2~4개 작업일, 실제 운영 검증은 그 뒤 최소 2거래일을 예상한다. 외부 공급원 장애와 추가 원인에 따라 조정한다. 공식 공급원 전환과 24~48시간 자원 측정에 기반한 최적화는 후속 1~2주 범위로 나누는 것이 적절하다. 이는 계획 추정이며 완료 보장이 아니다.

최종 완료는 ‘웹 배포 READY’가 아니라 **적용 버전 일치 + 운영 DB 정의 일치 + 시장별 예정 결과 저장 + Telegram 영수증 확인 + 연속 거래일 정상 운영**으로 판정한다.
