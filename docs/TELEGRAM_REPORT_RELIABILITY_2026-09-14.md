# MTN 텔레그램 보고 오류 분석과 재발 방지 개선안

작성일: 2026-09-14 KST. 대상: Telegram Web의 **추세매매 기록 봇** 대화, MTN 작업 로그, 운영 DB의 읽기 전용 조회, 현재 코드. 채팅 토큰·개인 식별자·인증값은 기록하지 않았다.

## 결론

실제 작업 실패와 반복 알림, 불명확한 보고 문구가 겹친 문제다. 단순히 에러 알림을 끄거나 작업자를 재시작하는 것으로 해결되지 않는다.

1. 일일 추천 보고는 나스닥 구성종목 수집 실패로 중단됐다. 최근 로그의 실패 9건은 모두 기존 Wikipedia 페이지에서 구성종목 표를 찾지 못한 오류다.
2. 9월 5일 스케줄 마이그레이션이 일반 작업의 HTTP 대기 예산을 280초에서 55초로 되돌렸다. 운영 DB 함수 정의와 실제 55초 시간초과 기록이 일치한다.
3. 동일 장애도 유예시간이 지나면 다시 알리는 감시 방식이 반복 메시지를 만든다. 실패 목록이 조금 바뀌어도 새 알림으로 처리됐다.
4. 종가 보고의 GREEN은 시장 방향이다. 수집 29/200인 날 엔진은 이미 추천을 차단했지만, 텔레그램은 차단 상태와 사유를 빼고 조건부 추천처럼 표시했다.
5. 미국 RS 전체 계산의 단일 요청 실행과 결과 저장의 `Gateway Timeout`은 별도 잔여 위험이다. 대기 예산 복원만으로 모든 시간초과가 해결된다고 단정할 수 없다.

아래 수정은 작업 폴더에 구현하고 검증한다. **운영 배포·운영 DB 마이그레이션 적용·작업자 재시작·실제 보고 재발송은 이번 작업에서 수행하지 않았다.** 운영 개선 완료 판정은 적용 후 실제 실행 결과를 확인해야 한다.

운영 조회 구간은 **9/9 09:00~9/14 00:50 KST**다. 이 구간에서 스케줄 실패 419건(`FAILED` 370, `TIMED_OUT` 49)을 확인했다. 시간초과 49건은 모두 55,000ms였고, 실패 응답 중 173건의 본문에 `Gateway Timeout`이 있었다. 이 수는 텔레그램 메시지 수가 아니라 스케줄 실행 실패 건수다. 9/12 17:49 KST 성공 백업 기록은 18:00 경고보다 11분 앞서므로, 백업 조회 실패가 빈 목록으로 해석됐을 가능성이 있다. 당시 조회 오류 원본은 확보하지 못해 추론으로 남긴다.

기존 [Wikipedia Nasdaq-100 페이지](https://en.wikipedia.org/wiki/Nasdaq-100)는 구성종목을 [별도 목록 페이지](https://en.wikipedia.org/wiki/List_of_NASDAQ-100_companies)로 안내한다. 현재 목록 HTML에서 102개의 고유 종목을 읽는 검증을 수행했다. 이 확인은 수집 코드의 복구 검증이며 종목 추천 자체의 검증은 아니다.

## 이번에 구현한 수정

### 1. 나스닥 종목 목록 수집 복구

- 대체 공급원의 주소를 실제 구성종목 목록 페이지로 수정했다.
- 고정 HTML id/열 순서 대신 Ticker·Company 헤더로 열을 식별한다. 열 순서, 태그, 각주 변경을 처리한다.
- 고유 종목 수가 100~150 범위를 벗어나면 불완전한 목록을 정상 처리하지 않는다. 기존 1차 공급원의 부분 응답도 대체 공급원으로 넘긴다.
- 두 공급원이 모두 실패하면 1차·대체 원인을 함께 기록해, 마지막 오류만 남아 원인을 잃지 않게 했다.
- 실제 공개 응답 및 모의 공급원 장애로 정상 102개 파싱, 부분 목록 거절, 대체 경로, 두 공급원 실패를 검증했다.

관련: `lib/finance/market/nasdaq-constituents.ts`, `lib/finance/market/scanner-universes.ts`, `tests/nasdaq-constituents.test.mjs`.

### 2. 스케줄 대기 예산 회귀 수정

- 기존 마이그레이션을 고치지 않고 후속 마이그레이션을 추가한다.
- 일반 작업 280초, 종가 작업 240초 예산을 유지하고 결과 수집기의 대기 판정도 같은 기준으로 맞춘다.
- 릴리스에 포함되는 마이그레이션 목록에 등록한다.
- 실제 운영 DB 정의가 55초로 되돌아가 있음을 읽기 전용으로 확인했다. 후속 SQL은 격리된 검증 환경에서 실행하며 운영에 적용하지 않는다.

관련: `supabase/migrations/20260914010000_restore_scheduler_timeout_budgets.sql`, `infra/release/production-scheduler-manifest.json`.

### 3. 반복 장애 알림 개선

- 최초 장애, 새 실패 항목, 악화, 전체 복구 때 알린다.
- 같은 장애가 유지되거나 실패 목록이 줄어드는 것만으로는 재발송하지 않는다.
- `MTN_ALERT_REMINDER_SECONDS=0`이 기본이다. 지속 장애를 다시 알릴 필요가 있으면 `43200`으로 12시간 간격을 설정할 수 있다.
- 정상 상태도 저장해 복구 이후 같은 장애가 다시 발생하면 새 장애로 알린다.
- 용량 측정 노후화에서 실제 한도 초과로 바뀌는 경우처럼 심각도가 같아도 원인이 다른 새 장애는 알린다.
- Telegram 응답 본문의 `ok`까지 확인하고, 상태 파일 손상을 처음 실행한 것으로 오인하지 않는다.
- Cloudflare KV를 선택할 수 있게 하되, 실제 연결을 새로 만들지는 않았다.

한계: Cloudflare Cache API는 서버 위치별 캐시이고 중간에 지워질 수 있다. TTL 30일은 보존 보장이 아니다. KV도 동시 실행의 원자적 처리를 보장하지 않는다. GitHub와 Cloudflare 감시가 동시에 다른 상태 저장소를 사용하면 각각 알림을 보낼 수 있다. 운영에서는 **텔레그램 발신 담당 감시기 하나를 지정**하고, 엄격한 중복 방지가 필요하면 아래 전달 원장 설계를 적용한다.

관련: `infra/cloudflare/health-deadman/worker.mjs`, `scripts/check-operations-health.mjs`, `.github/workflows/external-health-monitor.yml`.

### 4. 종가 보고의 보류 상태와 원인 표시

- 29/200 수집 보고의 제목을 ‘추천 보류’로 표시하고, 수집 부족 사유를 명시한다.
- 추천 상태와 시장 방향 GREEN을 별도 문구로 표시한다.
- 데이터가 불완전한 종목 풀은 정상 풀로 장기 캐시하지 않는다. 원천 수집 경고를 유지한다.
- 기존 추천 기준을 유지한다. 종목 수를 채우기 위해 기준을 낮추거나 추천을 만들어내지 않는다.

관련: `lib/closing-bet/data.ts`, `lib/closing-bet/telegram.ts` 및 종가 회귀테스트.

### 5. 용량 정보와 장애 분리

- 정보 임계치만 넘은 WATCH는 건강 상태를 저하시키지 않고 사용량 정보로 유지한다.
- 실제 경고·차단 임계치, 관측 누락·노후화 판정은 유지한다.
- 다른 장애가 복구됐을 때 약 258MiB라는 정보성 상태만으로 복구 통보가 막히지 않게 한다.

관련: `lib/operations/health.ts`, `tests/operations-health.test.mjs`.

## 적용 순서와 운영 확인

1. 이번 변경만 릴리스 대상으로 묶는다. 별도 작업의 화면 변경과 섞지 않는다.
2. 격리 SQL 검증, 회귀테스트, 타입 검사, lint를 통과시킨다. 운영 데이터 없이 보고 내용을 확인한다.
3. 운영 스케줄 함수의 현재 정의를 보관한 뒤 후속 마이그레이션을 적용하고, 일반280초/종가240초 및 수집 대기 기준을 다시 조회한다.
4. 앱과 작업자가 수정된 구성종목 수집 코드를 실행하도록 배포한다. 실패했던 과거 보고를 무조건 재발송하지 말고 날짜별 발행·전송 상태를 먼저 대조한다.
5. 감시 발신 담당을 하나로 정하고 새 정책을 적용한다. 상태 저장이 유지되는지 확인한다. 초기 상태 손실 시 한 번의 장애 알림이 다시 생길 수 있다.
6. 다음 정상 예정 실행에서 시장별 보고의 생성·저장·전달을 확인한다. 불완전한 시장은 보류 사유와 함께 표시한다.
7. 적용 후 연속 2거래일 관찰한다. 같은 장애의 반복 알림, 보고 누락, 55초 timeout 재발, 중복 발송, 잘못된 복구 성공이 없어야 완료로 판정한다. 주말 정상 상태만으로 장중 안정성을 확정하지 않는다.

문제가 생기면 변경된 앱·감시 버전만 이전 버전으로 되돌릴 수 있도록 준비한다. 스케줄 SQL은 55초 회귀를 재도입하는 롤백 대신 원인을 확인한 후속 교정으로 처리한다. 데이터 삭제나 실패 이력 초기화는 복구 수단으로 사용하지 않는다.
